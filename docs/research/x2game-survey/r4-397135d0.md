## 0. Method and what this range is

The classifier reads every function extent and its own strings, the call graph around the master DB
loader (`FUN_3960b820`, out of range), all `FUN_xxxxxxxx`/`0x3...` addresses cited by the existing
maps and by `crates/aa-client/src/port/**`, and the table names in the SQL strings. It then assigns
one area and one status per function: PORTED (address cited by a port source), MAPPED (address cited
by a MAP), COVERED (an existing crate implements the area), TO-PORT (client data/game logic with no
map and no crate), OUT (compiler/library/telemetry/framework), UNKNOWN (no classification).

This range is not the gameplay front end. It starts inside the client's **generated SQLite descriptor
loaders** (`FUN_397135d0` is the first `SELECT COUNT(*) FROM %s` table-container constructor **[R]**),
runs through the **X2 packet/archive codec**, the housing/vehicle/portal/interaction codecs and the
**formula/stat engine**, then ends in the statically linked support libraries and compiler fragments:

* `0x397135d0-0x397a6b9f`: descriptor loaders + generated table containers/STL instantiations;
* `0x397a6ba0-0x397ae85f`: doodad/prefab/housing/vehicle/portal gameplay and property setters;
* `0x397ae860-0x397d4fff`: archive field readers/writers for the packet families, tail interaction
  state;
* `0x397d5000-0x39896fff`: more descriptor loaders (siege/indun/zone/craft/item/quest/plot) with
  large generated STL/index blocks between them;
* `0x39897000-0x398b5fff`: client game logic (housing, interaction, combat cooldown, managers) and
  the f32 formula engine;
* `0x398b6000-0x398cb9ff`: HSUpdate/updater and the Tencent QOS SDK;
* `0x398cba00-0x398f8fff`: FreeType (TTF/Type1/CFF) plus its bundled zlib tail;
* `0x398f9000-0x3992a5ff`: zlib/libcurl 7.21.2 and the TDR anti-cheat protocol;
* `0x3998d160-0x3999a680`: C++ static initialisers of game-data globals;
* `0x39ac0000-0x3ac12241`: cold code islands (small getters/thunks/fragments).

The decompile has 65,230 headers for 65,437 `funcs.csv` rows in the whole DLL (the 207 without a
body are 141 thunks and 66 import/export stubs). In this range 17,724 of 28,761 rows are `Unwind@...` records and 351 are
catch/handler glue: 63% of the rows but only 7.6% of the bytes.

## 4. Findings and risks

1. **The range is dominated by generated data/framework code, not gameplay.** 5,725 functions /
   1,043.3 KB (46% of all bytes) are generated table containers, validators and STL instantiations;
   the 430 master-loader callees are only 246.7 KB. Treating all of it as a line-by-line port would be waste:
   `rusqlite` + Rust std covers the mechanism, while the table semantics are the real contract.
2. **283 loader functions / 131.9 KB have no owner.** The largest are quests (75), doodad funcs
   (58), skills/effects/buffs (41) and items (19). `aa-client` already reads 122 of the 405 loaders'
   tables; the rest are the data-side gap. This is not proof that every table is needed: some are
   client-only preloads that the server paths already carry **[I]**, but the survey cannot rule them
   out without opening each window.
3. **Packet/archive codec is 1,136 functions / 137.7 KB and is only covered, not proven equal.**
   `aa-net` implements the protocol from the server contract; this codec is the client's original
   `IArchive` field order. Specific housing/vehicle/portal/interaction packets have maps (and 85
   ported functions), but a blanket packet equality test against this codec does not exist.
4. **The formula engine is both mapped and ported.** 44 functions / 17.3 KB; 31 addresses are cited
   by `port-formulas/MAP.md`, 13 are cited by `crates/aa-client/src/port/formulas`. This is the
   strongest-covered game-logic area in the range.
5. **One lightly mapped gameplay block:** `0x3989d4-0x3989ff` (aimbox/aimPoint parser, cast/effect
   helpers, damage debug dump) is only covered by the generic "aa-client combat" claim, not by a
   MAP address. 77 functions / 14.7 KB in `0x3989d400-0x398a1000`; the nearby stat functions
   (`0x3989f900`, `0x398a0bc0`, ...) are mapped. Verify this block when the owner next touches
   targeting/casting.
6. **Statically linked libraries are a large share of the bytes:** FreeType 173.5 KB, libcurl
   139.8 KB, HSUpdate 69.8 KB, zlib 23.3 KB, QOS 14.4 KB, TDR 14.0 KB. Only FreeType/zlib map to a
   current crate (`aa-ui`/Bevy text, `aa-pak`); the rest are telemetry/anti-cheat/web and should stay
   OUT.
7. **Compiler artefacts inflate the row count:** 17,724 unwind records + 351 handlers = 18,075
   rows, i.e. 63% of the range's rows, but only 174.0 KB. The "28,761 functions" headline is mostly
   metadata; real code is 10,510 functions / 2,053.4 KB.

## 5. Limits

* Table coverage is a name-occurrence heuristic over `crates/**/*.rs`; it does not prove columns,
  defaults or row order. `aa-client` often reads only the columns a window needs.
* Areas are assigned by address neighbourhood, call cluster and strings. The generated STL blocks
  have no strings; only 2,163 of the 11,037 non-unwind functions have any string at all. Boundary
  functions can therefore be off by one area, but the status totals are exhaustive.
* `MAPPED` only means an address is cited by a map, not that the whole area is mapped. The map docs
  remain the authority for behaviour.
* `funcs.csv` includes unwind records and catch glue; the decompile emits only metadata stubs for
  most of them. This survey does not try to read those (they are OUT).
* No live client, server or lane was used for this survey: it is static binary/decompile research.

## 6. Reproduce

```powershell
python -I -u tools/x2game_survey/survey_range.py
python -I -u tools/x2game_survey/survey_range.py --check
```

The script prints the per-status totals and the group table and writes the per-function classification
to `data/extract/x2game-survey/r4-classification.tsv` (git-ignored). `--check` re-reads that artifact and
asserts it covers the `funcs.csv` range exactly, with unique addresses and only the six statuses.
Verified on 2026-10-26: 28,761 functions, 2,278,266 bytes.

## 7. Pending live checks

None. This survey is static: every result comes from `funcs.csv`, the decompile, strings/xrefs, the
call graph and the existing maps/ports. No original-client oracle call is required to classify a
function. A future differential check of the packet codec (drive the original archive reader/writer
with synthetic archives) or of individual DB loaders (compare loaded tables) would need the hidden
client/driver, but those are porting tests, not survey gaps, and are out of scope here.
